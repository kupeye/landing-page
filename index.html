Why upgrades stall

Every release moves the ground under your clusters.

3releases a year

Kubernetes ships about three minor versions a year, and each one deprecates, removes or changes something you run.

6×the price of waiting

Fall behind on EKS and each cluster bills $0.60 an hour in extended support instead of $0.10, for up to 12 more months.

1hop at a time

Control planes move one minor version per upgrade, so every release you skip adds another hop to the plan.

Owned attribution

Warnings say something is deprecated. KupEye says who.

Every deprecated call in your audit log is traced from the request to the team that can fix it, with a confidence score on every link. Weak links are suggested, never assigned.

Metrics and audit, together

Reads the apiserver_requested_deprecated_apis metric and audit annotations, keeps 90 days including reads, and feeds the same numbers to Grafana.

Identity over time

Joins service accounts and Pod IPs by time window, so short-lived Jobs and CronJobs don’t slip through.

Ends at a person

Owners come from CODEOWNERS or namespace labels, so each fix lands with the team that can make it.

Readiness, end to end

Everything that can break an upgrade, checked in one place.

API removals are only the start. KupEye also checks the nodes, add-ons, storage and behaviour changes that catch teams out halfway through an upgrade.

Nodes and runtimes

A read-only probe checks every node for cgroup v1, containerd 1.x, kube-proxy in ipvs mode and the old CRI v1alpha2 API, before a new kubelet finds out the hard way.

prod-eu-1 · 32 nodes 6 on cgroup v1 26 ready

Behaviour, not just apiVersion

Open CEL rules catch changes that keep the same API but break your workloads, like static Pods losing Secret references in v1.37 or SELinux mount labels on shared volumes.

id: static-pod-secret-ref
since: v1.37
match: |
  has(object.metadata.annotations['kubernetes.io/config.mirror'])
  && object.spec.volumes.exists(v, has(v.secret))

Add-on compatibility

An open matrix of which operator and add-on versions run on which Kubernetes versions, reviewed in public.

Drain simulation

Replays each node drain against PodDisruptionBudgets and the scheduler, so a stuck drain shows up in the plan, not in production.

Upgrade rehearsal

Applies your real manifests to a throwaway API server on the target version and lists everything it rejects.

Storage migration

Finds objects stored at old CRD versions and drives StorageVersionMigration, GA in v1.37, before a version is dropped.

Rollback readiness

Marks every point of no return in the plan, and the provider windows that matter, like the 7 days EKS allows to roll a control plane back.

Plan and gate

A path, not a guess.

KupEye plans each hop from where you are to where you need to be, keeps nodes inside the supported kubelet skew, and shows what every month of waiting costs.

  1. Today v1.34 Control plane and nodes
  3. Hop 1 v1.35 Control plane Rehearsal passes
  5. Hop 2 v1.36 Control plane No removed APIs called
  7. Hop 3 v1.37 Control plane CRD storage migrated
  9. Node roll v1.37 All node pools, once cgroup v2 · containerd 2

Nodes stay on v1.34 through every control-plane hop, inside the three-minor kubelet skew, then roll once.

KupEye never runs your upgrade. It answers the gate, so the tools you already trust go ahead only when the evidence is clean.

  • Cluster API hooks

How it works

From install to a green gate in three steps.

  1. 01

    Install the agent

    One read-only Helm chart per cluster. It connects out over mutual TLS, so there are no inbound ports to open and no VPN to run.

  2. 02

    Collect the evidence

    Stored objects, live API calls, audit identities, nodes and add-ons, checked against a signed knowledge base generated from the Kubernetes source.

  3. 03

    Plan, fix and gate

    Get the hop-by-hop path, owners notified, pull requests opened, and a gate your pipeline can wait on.
